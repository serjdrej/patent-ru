# Поиск: API Роспатента (ИС ПП) — проверенная методика

Загружайте этот файл, когда: нужно найти аналоги или уровень техники по российскому и советскому патентному фонду (RU/SU) через API Поисковой платформы Роспатента — запрос, извлечение дословной формулы, датная дисциплина, работа с `similar_search`, классификаторы.

> Всё ниже получено эмпирически в боевом прогоне 08.09.2026 по заявке № ⟦НОМЕР ЗАЯВКИ⟧/07(⟦ДОСЬЕ⟧), а не из документации. Официальная инструкция (`Открытые_API_ИС_ПП.md`) этих вещей не содержит либо описывает иначе. **Это ядро ценности скилла — раздел перенесён дословно из рабочего брифа и не должен переписываться без нового боевого прогона.**

## 1. Подключение

```
BASE = https://searchplatform.rospatent.gov.ru/patsearch/v0.2
Заголовки: Authorization: Bearer <ключ>
           Content-Type: application/json
```

Ключ (jwt) выдаётся только зарегистрированному пользователю в разделе «Генерирование ключей» интерфейса ИС ПП.

**Дисциплина ключа — жёсткое правило, см. также `SKILL.md`:**
- ключ читается **только** из переменной окружения `ROSPATENT_API_KEY`;
- никогда не записывается в код, в сохраняемые JSON, в логи и в отчёты;
- при отсутствии переменной скрипт завершается с внятным сообщением, а не запрашивает ключ в диалоге;
- пользователю предлагать запуск через терминал, а не пересылку ключа в переписку.

**Удобный вариант для повторного использования ключа (Windows)** — `scripts/rospatent-set-key.ps1` (разово, скрытым вводом сохраняет ключ в `.secrets/rospatent_key.enc`, зашифрованным Windows DPAPI — не открытым текстом) и `scripts/rospatent.ps1` (расшифровывает и подставляет ключ только дочернему процессу `python.exe` на время одного вызова; ни в системные переменные среды Windows, ни куда-либо ещё ключ не попадает и после завершения скрипта нигде не остаётся). `.secrets/` целиком исключён из git, кроме `README.txt` с инструкцией. `rospatent.py` при этом не меняется и по-прежнему читает ключ только из окружения — обёртки лишь избавляют от необходимости вводить `$env:ROSPATENT_API_KEY = ...` в каждом новом окне PowerShell.

DPAPI защищает файл на диске (бэкап/синхронизация/кража диска не отдадут ключ в открытом виде) — это не то же самое, что изоляция «только для этого скрипта»: любой процесс, запущенный под вашей же учётной записью Windows, технически способен вызвать те же DPAPI-функции и расшифровать файл. Подробности и обоснование — в комментарии в начале `scripts/rospatent-set-key.ps1`.

## 2. `POST /search` — рабочая лошадь

```json
{"q": "<запрос>", "limit": 10, "sort": "relevance",
 "filter": {"country": {"values": ["RU", "SU"]}}}
```

- Синтаксис Elasticsearch-подобный: `AND` / `OR`, усечение `*`, фразы в кавычках, скобки.
- **`limit: 20` на широких запросах падает с `IncompleteRead`.** Держать `limit ≤ 10`, при необходимости добирать через `offset`.
- Фильтр `country` принимает коды ST.3. Для российского фонда — `["RU", "SU"]` (советские авторские свидетельства входят в уровень техники и реально всплывают: в прогоне найден `RU239U1_19950116`).

**Формулировка запроса решает всё.** Эмпирика:

| Запрос | Итог |
|---|---|
| `сверхширокополосный AND (лазерн* AND (фотоприемн* OR фотодиод*))` | 28 документов, **все мимо** — генераторы СШП-импульсов, туннельные фотодиоды |
| `"опорная плоскость" AND (высотн* AND координат*) AND радио*` | **0** — многословные фразы в кавычках хрупкие, избегать |
| `(веха OR "измерительная штанга") AND (инерциальн* OR "датчик наклона") AND координат*` | 15 документов, **из них 3 решающих** |
| `(нивелир OR "лазерный передатчик") AND "фотоприемное устройство" AND (координат* OR высот*)` | 17 документов, 3 релевантных |

**Рабочий шаблон запроса:** `<существительное формы-фактора> AND <существительное датчика> AND <измеряемая величина>`, где все три — принятые в отрасли термины, а не бытовые синонимы. «Веха», «нивелир», «фотоприемное устройство», «опорная высотная координата» дают попадания; «портативное устройство», «лазер», «позиционирование» — шум.

## 3. `GET /docs/<id>` — дословные формулы

**Идентификатор обязан содержать дату публикации:** `{код страны}{номер}{вид документа}_{ГГГГММДД}`, например `RU2794881C1_20230425`. Без суффикса даты запрос не разрешается.

**Обходной путь, если даты нет:** `POST /search {"q": "PN=RU2794881C1", "limit": 1}` → взять `id` из выдачи → повторить `GET /docs/<id>`. В скрипте реализовано автоматически.

**Структура ответа** (поля, которые реально нужны):

| Путь | Содержимое |
|---|---|
| `biblio.ru.title` | название |
| `biblio.ru.patentee[].name` | патентообладатель |
| `common.publication_date` | дата публикации, формат `ГГГГ.ММ.ДД` |
| `abstract.ru` | реферат |
| `claims.ru` | **полная формула, все пункты одной строкой** |

Текст приходит с HTML-тегами и маркерами вида `[135]` — чистить регулярным выражением `<[^>]+>` и `\[\d+\]` перед показом.

## 4. `POST /similar_search` — **не доверять**

```json
{"type_search": "text_search", "pat_text": "<текст п.1>", "count": 100}
```

Метод существует и отвечает, но **в боевом прогоне оказался негодным**: на текст п.1 формулы геодезического прибора (1448 знаков) выдал 100 документов, у которых `similarity_norm` уложилась в диапазон **0.9931–0.9942** — метрика не различает. В первой двадцатке: отслеживание движения в МРТ, конфигурация RRC в EN-DC (Ericsson), классификация контента (Nokia), сеть беспроводной связи с транзитными участками (Qualcomm).

**Правило для скилла:** `similar_search` допустим только как генератор идей для последующих ключевых запросов. **Категорически запрещено** использовать его результаты как доказательство отсутствия аналогов или как ранжированный список ближайшего искусства. Если метод применён — писать в аудит, что метрика не дискриминирует.

Единственная польза в прогоне: в топе оказался `RU2841878C1` (ЭНВИСОЛ), который затем подтвердился как реальный ближайший RU-аналог по системной архитектуре. То есть сигнал есть, но тонет в шуме.

## 5. Дисциплина исполнения

- 1 запрос в секунду, последовательно, ответ дождаться до следующего вызова.
- При сетевой ошибке — пауза 3 с, одна повторная попытка, затем фиксация отказа в аудите.
- Три-счёт: запросов отправлено / документов получено / документов процитировано.
- **Датная дисциплина:** отсекать по `publication_date` относительно даты приоритета проверяемой заявки. В прогоне четыре документа оказались опубликованы **после** приоритета (`RU2866163C1_20260714`, `RU243533U1_20260519`, `RU2859185C1` и `RU2859187C1` от 31.03.2026) — в уровень техники они не входят, но их легко принять за аналоги. Помечать явным флагом, а не молча выбрасывать.

## 6. Что API даёт сверх поиска

- `GET /datasets/tree` — перечень поисковых массивов, **проверено вживую 08.09.2026 дважды (с реальным ключом)**. Первоначальная догадка брифа про ID вида `cn_pmi`/`kr_pmi`/`ch_pmi`/`dwpi` **не подтвердилась — таких ID нет**. Реальный список: `ru_till_1994`, `ru_since_1994`, `cis`, `dsgn_ru` (Россия/СНГ), затем минимум РСТ — `cn`, `kr`, `ch`, `jp`, `ep`, `de`, `fr`, `gb`, `au`, `ca`, `at`, `us`, `pct`, `ap` (ARIPO/OAPI), отдельно промышленные образцы `dsgn_kr`/`dsgn_cn`/`dsgn_jp`, и `others` (страны с малым фондом).
- **Два независимых, пересекающихся механизма зарубежного поиска — не один.** ⚠️ Более ранняя версия этого раздела утверждала «это не отдельный механизм, а тот же фильтр `country`» — **формулировка была излишне категоричной**, основана на одном успешном тесте `--country CN`, а не на сверке с документацией. По официальной инструкции (раздел 2.2.10) `datasets` — самостоятельный, отдельно документированный параметр тела `POST /search` (пример из инструкции: `{"q": "ракета", "datasets": ["cis"]}`), а не побочный эффект `filter.country`. Оба параметра работают и, судя по всему, частично перекрываются, но это разные вещи:
  - `filter.country.values: ["CN"]` — фильтр по стране публикации документа. Проверено: `rospatent.py search "laser" --country CN` вернул реальные китайские патенты (`CN116113149A_20230512` и т. п.) из фонда 1.3 млн документов.
  - `datasets: ["cn"]` — фильтр по поисковому массиву (может не совпадать 1:1 со страной публикации — не проверено, чем массив отличается от простого странового фильтра на практике). Добавлен в `rospatent.py` (`--datasets`, обычно вместе с `--world`, иначе умолчание RU,SU обнулит выдачу). Живым запросом с `--datasets` пока не протестирован — при использовании относиться как к ⚠️, не как к ✅.
  Оба канала не подвержены антибот-блокировкам Google Patents (раздел «Другие механизмы доступа» `search-international.md`) — заходят через тот же ключевой API.
- `POST /classification/ipc/search/` и `/classification/ipc/code/` — работа с МПК. Закрывает задачу выбора индекса при подготовке заявки (используется в `draft-application.md`). Реализовано в `rospatent.py` (`ipc --query`/`ipc --code`), проверено вживую 08.09.2026: `ipc --code "G01C 15/00"` вернул иерархию классификатора.
  **Поле МПК в текстовом запросе `q` — `IC=`, не `IPC=`.** Проверено против официальной инструкции (раздел про сокращения поисковых полей): `IC=A61K31/00`, `IC=A01B19` и т. п. — `IPC=` в документации не встречается и, по опыту прогона, отдаёт `HTTP 400`. Именно class-restricted запрос через `IC=` в одном живом деле вскрыл документ, изменивший вердикт поиска — не пропускать этот шаг (см. также `search-workflow.md`, «CPC/МПК follow-up»).
- `group_by: "family:docdb"` / `"family:dwpi"` — разрешение патентных семей, снимает двойной счёт. Добавлено в `rospatent.py` (`--group-by`), не проверено живым запросом отдельно от `datasets` — при использовании сверять результат вручную.

**Дополнительные находки прогона 08.09.2026 (после первой публикации этого раздела):**
- Записи с кодом вида `A` (application) в `id`/`kind` содержат только библиографию — полный текст (формула, описание) там пуст. Для дословного текста нужна именно запись `A1` (или иной кодовый суффикс публикации с полным текстом), не `A`.
- Номера заявок/патентов США дополняются нулями до десяти знаков при формировании идентификатора документа — короткий номер без ведущих нулей не находится.
- В ответах `/docs` есть поля `prototype_docs` и `referred_from` — бесплатный аналог графа цитирования (citation graph), которого не хватало без Lens.org (см. `search-international.md`, «Citation-graph через Lens.org — вне периметра»). Не задействовано в `rospatent.py` — доработать при необходимости; полезно для `draft-application.md` (выбор прототипа) и для ландшафтного поиска (`search-workflow.md`).

## 7. Готовые скрипты — отправная точка, а не задание

Лежат в `scripts/rospatent.py`. Написаны и отлажены 08.09.2026, прогнаны на реальных файлах дела. **Дорабатывать, а не переписывать с нуля.** Чистый stdlib, без зависимостей, с русскими сообщениями и CLI.

Внутри уже реализованы все обходные пути раздела 2–5: автоподбор даты публикации через `PN=` при неполном идентификаторе, `SAFE_LIMIT = 10` с предупреждением, одна повторная попытка через 3 с (на 4xx не повторяет), пауза 1 с между вызовами, три-счёт с перечнем отказов, `strip()` для снятия HTML и маркеров `[135]`, `fields()` для разбора ответа `/docs`, пометка документов позже даты приоритета. В `similar` встроена автопроверка: если разброс `similarity_norm` меньше 0.05, печатается предупреждение о непригодности метрики.

```bash
python scripts/rospatent.py --priority 2026-03-23 search '(веха OR "измерительная штанга") AND инерциальн*'
python scripts/rospatent.py doc RU2816552C1_20240401 RU2794881C1      # второй — дату подберёт сам
python scripts/rospatent.py datasets                                   # список массивов (информационно)
python scripts/rospatent.py search "laser" --country CN                # зарубежный фонд — тот же search
python scripts/rospatent.py search "laser" --world                     # вообще без фильтра по стране
```

**Известное ограничение:** `rospatent.py` пока не разрешает патентные семьи (`group_by`) и не работает с классификаторами МПК — оба метода в API есть (раздел 6), доработать при необходимости.
