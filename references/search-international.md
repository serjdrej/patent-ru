# Поиск: зарубежные источники (fallback-канал)

Загружайте этот файл, когда: нужны аналоги за пределами RU/SU-фонда (US/EP/CN/JP/KR/WO), или когда нужно понять, почему прямой доступ к Google Patents/Espacenet/USPTO периодически не работает и как его правильно обходить.

## Почему это не основной канал

В боевом прогоне 08.09.2026 прямой доступ к зарубежным источникам оказался хрупким; из семи ближайших аналогов дословную формулу удалось получить ровно для одного. Для российского фонда за то же время API Роспатента отдал 15 дословных формул без единого отказа (см. `search-rospatent.md`). Живая проверка 08.09.2026 (раздел 2 ниже) объяснила механизм отказов и дала рабочий обход — это не значит, что канал стал основным, но fallback стал заметно надёжнее.

**Порядок каналов для дела, которое рассматривает ФИПС:**
1. **API Роспатента, зарубежный фонд.** ✅ Проверено вживую 08.09.2026 реальным ключом: `python rospatent.py search "laser" --country CN` вернул настоящие китайские патенты из фонда 1.3 млн документов, фильтром `filter.country.values` — тем же механизмом, что и для RU/SU, просто с другим кодом (`CN`, `KR`, `CH`, `JP`, `EP`, `DE`, `FR`, `GB`, `AU`, `CA`, `AT`, `US`, `PCT`, `AP`; полный список — `GET /datasets/tree`, см. `search-rospatent.md`, раздел 6). Есть и второй, отдельно документированный параметр `datasets` (та же команда с `--datasets` вместо `--country`) — оба реализованы в `rospatent.py`, подробный разбор чем они отличаются на практике — в `search-rospatent.md`, раздел 6. Не подвержен антибот-блокировкам Google Patents вообще — заходит через ключевой API. **Первый выбор, если `ROSPATENT_API_KEY` доступен.**
2. **Google Patents** — по методике раздела 2 ниже (не по методике «просто открыть страницу патента»).
3. **Espacenet** — публичный веб-поиск (`worldwide.espacenet.com`) на 08.09.2026 отдал HTTP 403 на прямой запрос без авторизации, это тупик. **Но у Espacenet есть официальный API — EPO OPS** (раздел 4.2), с обычной для таких сервисов моделью (бесплатная регистрация + ключ) — именно его использовать, не веб-скрейпинг публичной страницы.
4. **USPTO** — по методике раздела 3 ниже. Короткая версия: своей внутренней API у Patent Public Search пользоваться можно, но только живым браузером — скриптом её не автоматизировать надёжно; для одиночной проверки американского аналога проще и надёжнее закрыть вопрос через Google Patents (раздел 2), который US-фонд тоже индексирует.

**Итог для практики — какой сценарий удобнее и когда:**

| Ситуация | Что использовать |
|---|---|
| `ROSPATENT_API_KEY` доступен (см. `search-rospatent.md`, раздел про `scripts/rospatent.ps1`) | **`rospatent.py search ... --country <код>`** — первый выбор: ✅ проверено вживую, не подвержено антибот-блокировкам, тот же клиент и дисциплина, что для RU/SU (раздел 1 выше) |
| Ключа нет или нужна конкретно страна вне списка `datasets/tree` | **`scripts/google_patents.py`** (раздел 2) — без регистрации, без биллинга, работает прямо сейчас, покрывает не только US, но и EP/CN/JP/KR/WO |
| И `rospatent.py`, и `google_patents.py` недоступны/заблокированы | Espacenet/EPO OPS (раздел 4.2) или зарегистрировать ODP-ключ USPTO — по обстоятельствам |
| Регулярный/массовый зарубежный поиск ожидается по многим будущим делам, а не разово | Стоит один раз зарегистрироваться в **EPO OPS** (раздел 4.2) — 5 минут, бесплатно, без верификации личности; после регистрации это официальный API уровня Роспатента, отдельный от хрупкого веб-скрейпинга Espacenet |
| Нужен полнотекстовый поиск по всему корпусу (SQL, тысячи документов, аналитика) | **Google Patents Public Datasets на BigQuery** (раздел 4.1) — не для одиночного запроса, а для инфраструктурной задачи; требует GCP-проект, решение пользователя |
| US-специфичные метаданные (статус делопроизводства, PTAB) обязательны | Вручную через `ppubs.uspto.gov` в браузере (раздел 3) — не скриптом |

**Не рекомендуется как первый выбор для этого скилла:** сторонняя библиотека `patent-client-agents` (раздел 4.3) — она мощнее и покрывает больше юрисдикций, но это внешняя зависимость, не проверенная нами end-to-end; `scripts/google_patents.py` уже закрывает типовую задачу и был проверен лично.

## 2. Google Patents — что именно ломается и как обходить (проверено 08.09.2026)

Прежняя формулировка («лимит по IP, HTTP 503 на шести запросах подряд») была верна по симптому, но не объясняла механизм. Прямая проверка вживую в этой сессии дала точную картину.

### 2.1. Два разных ресурса с разной терпимостью к автоматическим запросам

| Ресурс | Поведение на автоматический запрос |
|---|---|
| `GET patents.google.com/patent/<ID>/<lang>` (страница конкретного патента — то, что нужно для дословной формулы) | **В этой сессии блокировался почти сразу**, вплоть до первого запроса. Ответ — HTML-страница «Sorry... but your computer or network may be sending automated queries», статус то `200`, то `503` (тело одинаковое в обоих случаях — **проверять не только код ответа, но и наличие `Sorry` в теле**). ⚠️ См. раздел 4.3 — независимая проверка на другом IP/сессии показывает, что этот же ресурс при аккуратном темпе (≥4 с между запросами) работает как основной канал, а не блокируется с первого обращения. Похоже, дело не в самом ресурсе, а в репутации конкретного IP на момент теста — не считать блокировку неизбежной. |
| `GET patents.google.com/xhr/query?url=...` (тот же JSON-эндпоинт, которым пользуется сама страница поиска) | Терпимее: в прогоне выдержал ~8–12 запросов подряд без пауз и без заголовков, прежде чем тоже свалился в `503` после продолжительной активности (смешанной с обращениями к заблокированному ресурсу выше) |
| `GET patentimages.storage.googleapis.com/<путь>.pdf` (PDF патента, отдельный хост — облачное хранилище, не `patents.google.com`) | **Не блокируется вообще** — оставался доступен (`200`), даже когда `patents.google.com` целиком отдавал `503` по всем путям |

**Вывод для этого скилла: связка `xhr/query` → PDF (раздел 2.2) остаётся основной** — она проще, не требует парсинга HTML/DOM и не зависела от репутации IP в тесте. Но `/patent/<ID>` **не обязательно исключён навсегда** — если связка через PDF даёт плохой текст (перемешанные колонки, скан без слоя), можно пробовать страницу патента напрямую с темпом ≥4 с между запросами и ретраями с бэкоффом (раздел 4.3); просто не ожидать, что это сработает с первой попытки на любом IP.

### 2.2. Рабочая связка «поиск → дословный текст»

**Шаг 1 — поиск через JSON-эндпоинт, не через HTML-страницу:**

```
GET https://patents.google.com/xhr/query?url=q%3D<url-encoded запрос>[%26country%3D<код страны>]&exp=&tags=
```

Синтаксис запроса внутри `q=` — тот же Elasticsearch-подобный стиль, что и у API Роспатента: `q=(term1+term2)` — AND в скобках; `q=%22точная+фраза%22` — фраза в кавычках. Фильтр по стране — отдельный параметр `country`, дописанный в конец значения `url=` через `%26` (пример рабочего вызова: `url=q%3D(surveying+pole+photodetector)`, с фильтром — `url=q%3D(...)%26country%3DRU`).

Ответ — JSON, без парсинга HTML: `results.total_num_results`, `results.cluster[0].result[]`, у каждого элемента —
`id` (вида `patent/US10725123B2/en`), `patent.title`, `patent.snippet` (усечённая цитата, часто прямо из формулы — годится для быстрой оценки релевантности, но **не как дословный п.1**, он обрезан), `patent.priority_date` / `filing_date` / `publication_date` / `grant_date`, `patent.inventor`, `patent.assignee`, `patent.publication_number`, **`patent.pdf`** (относительный путь к PDF, может быть пустым — тогда для этого хита PDF через Google недоступен), `patent.family_metadata.aggregated.country_status[]` (список стран семьи с состоянием `ACTIVE`/`NOT_ACTIVE` — закрывает и семейное разрешение, и грубую FTO-проверку статуса за один вызов, без отдельного скрипта).

**Шаг 2 — дословный текст формулы через PDF, не через страницу патента:**

```
GET https://patentimages.storage.googleapis.com/<значение поля patent.pdf из шага 1>
```

Извлечь текст:

```bash
pdftotext -layout patent.pdf -   # -layout критичен: многие патенты двухколоночные, без него текст перемешивается
```

Искать раздел формулы по маркеру — он зависит от языка/юрисдикции документа: `What is claimed is:` / `The invention claimed is:` / `I claim:` (US); у не-US документов может отличаться, маркер придётся подбирать по факту. **Не искать по одному слову `Claims`** — оно ложно совпадает с «disclaimer» и с библиографической строкой вида «20 Claims, 10 Drawing Sheets», нужна словесная граница и точная фраза. **Если PDF — скан без текстового слоя** (старые документы, реже у пост-2000 US/EP/WO), `pdftotext` вернёт пусто — тогда помечать хит как «текст формулы не извлечён», как и раньше. Даже с `-layout` разметка двухколоночных патентов иногда перемешивается на границах колонок — **сверять полученный текст глазами перед тем, как цитировать его как дословный**, не доверять экстракции слепо.

**Готовый скрипт** — `scripts/google_patents.py`, реализует эту связку целиком и уже не ходит на `/patent/<ID>`:

```bash
python scripts/google_patents.py search "(surveying pole photodetector)" --country RU --limit 10
python scripts/google_patents.py claims 26/37/74/5232ba04f9da8e/US10725123.pdf   # путь — из поля patent.pdf выдачи search
```

Проверено 08.09.2026: `search` и `claims` отрабатывают отдельно (протестировано на живом хите, дословная формула извлечена корректно); если `patents.google.com` целиком заблокирован, `search` вернёт внятную русскую ошибку и подскажет следующий шаг, а `claims` по уже известному пути `pdf` всё равно отработает — хост PDF отдельный.

### 2.3. Дисциплина при блокировке

- Как только `/xhr/query` тоже начал отдавать `503` — блокировка перестаёт быть точечной (по одному ресурсу) и становится общей на весь `patents.google.com`. **Пауза 30 с блокировку не снимает** (проверено); закладывать паузу в минутах, не в секундах, и в рамках одной сессии поиска — не долбить `patents.google.com` повторными попытками, а переключаться на Espacenet/Rospatent-зарубежные-массивы.
- `patentimages.storage.googleapis.com` в это время обычно остаётся живым — если `pdf`-путь уже получен раньше (из более ранних успешных вызовов `xhr/query`), продолжать вытягивать PDF-ы даже после блокировки самого `patents.google.com`.
- Симптом блокировки — не только код ответа: тело `<title>Sorry...</title>` с текстом «automated queries» приходит и с `HTTP 200`, и с `HTTP 503`. **Проверять содержимое, не только код.**
- Эта картина получена от одного IP в одной сессии 08.09.2026 — сколько именно запросов до блокировки и сколько длится блокировка, зависит от текущей репутации IP и может отличаться в другой сессии. Не считать конкретные числа («8–12 запросов», «30 с не хватает») константой — переопределять эмпирически в начале каждой сессии поиска.

## 3. USPTO — что сломано, что жив, и почему скриптом не взять (проверено 08.09.2026)

Прежняя формулировка («старые сканы без текстового слоя») касалась только качества конкретных документов. Живая проверка нашла более серьёзную структурную проблему: у USPTO **три разных пути доступа с разной судьбой**, и ни один не даёт того, что API Роспатента даёт для RU-фонда — стабильного, ключ-в-руки, скриптуемого API.

### 3.1. Три пути и что с каждым не так

| Путь | Статус на 08.09.2026 |
|---|---|
| **Legacy PatentsView API** (`api.patentsview.org/patents/query`, `search.patentsview.org`) | **Мёртв.** `api.patentsview.org` отдаёт `301` на страницу `data.uspto.gov/support/transition-guide/patentsview`: с 20.03.2026 PatentsView переезжает на новый портал USPTO (ODP), старый API временно недоступен, **даты возврата функций поиска нет** ни на одну из страниц. `search.patentsview.org` не резолвится вовсе. Старые ключи API для нового портала не действуют. |
| **USPTO Open Data Portal API** (`data.uspto.gov`, включает Patent File Wrapper API — замена PatentsView) | Технически жив и документирован (Swagger UI, синтаксис запросов, лимиты) — это официальная будущая замена. **Но требует API-ключ, а ключ выдаётся только после привязки верифицированного аккаунта ID.me** (американская система идентификации личности) к учётной записи USPTO.gov. Это заведомо более тяжёлый барьер, чем «Генерирование ключей» у Роспатента — **не пытаться проходить эту регистрацию автоматически**, это шаг для пользователя, если он вообще технически осуществим без американских документов. |
| **Patent Public Search** (`ppubs.uspto.gov`, официальный бесплатный веб-инструмент, замена старым PatFT/PatImg) | Сама страница открывается (`200`), поиск работает **и живьём отдаёт структурированный JSON**, включая довольно свежие документы (в прогоне встретились патенты с датой публикации 08.09.2026 — сегодняшним числом). Но у API — **сессионная, короткоживущая авторизация**: анонимная сессия создаётся автоматически при заходе на страницу (`POST /api/users/me/session`), однако токен/`queryId` этой сессии протухает в пределах одной-двух минут активности — повторный вызов того же самого документа JSON-эндпоинта `/api/patents/highlight/<ID>` через десятки секунд после первого вернул `401`. **Голым `curl` без предварительной живой сессии браузера эту API не взять**; воспроизводимо только через реальный браузер (`mcp__Claude_Browser__*` в этом окружении), не как самостоятельный скрипт. |

### 3.2. Рабочие эндпоинты Patent Public Search (для справки, не для слепой автоматизации)

Обнаружены вживую при поиске через UI (`ppubs.uspto.gov`):

- `POST /api/searches/searchWithBeFamily` — основной поиск, тело запроса включает `q` (текстовый запрос), `databaseFilters` (`US-PGPUB`/`USPAT`/`USOCR`), `op` (`OR`/`AND`/...). Ответ — JSON с массивом `patents[]`: заголовок, заявитель/патентообладатель, даты подачи/публикации, IPC/CPC-коды, и постранично — **где именно в документе начинается и заканчивается раздел формулы** (`claimsStart`/`claimsEnd`), описания (`descriptionStart`/`descriptionEnd`) и т. д.
- `GET /api/patents/highlight/<GUID>?queryId=<id>&source=USPAT&includeSections=true` — отдаёт HTML-фрагменты документа (`abstractHtml`, `descriptionHtml` подтверждены вживую содержательным текстом, не сканом; наличие отдельного `claimsHtml` не подтверждено напрямую в этой сессии, но по структуре ответа — вероятно).

Оба эндпоинта требуют актуальную сессионную куку и (для второго) свежий `queryId` из ответа первого — воспроизводить их в изолированном скрипте не пытаться, пока не появится решение через ODP API (раздел 3.1) с ключом.

### 3.3. Практический вывод

- **Не писать скрипт под `ppubs.uspto.gov`** — то, что он технически отвечает JSON-ом, не делает его скриптуемым источником: сессия слишком короткоживущая. Если US-документ нужен через живой браузер интерактивно — можно, но это не тот же режим работы, что `rospatent.py`/`google_patents.py`.
- **Не пытаться зарегистрировать ключ ODP API за пользователя** — шаг требует ID.me-верификации личности, это решение и действие пользователя, не агента.
- **Для практической задачи «проверить американский аналог» — использовать Google Patents (раздел 2)**, который индексирует и US-фонд, а связка `xhr/query` + PDF-CDN уже проверена и скриптуема. USPTO как отдельный канал добавляет ценность в основном там, где нужны специфические для USPTO метаданные (`claimsStart`/`claimsEnd`, статус делопроизводства, PTAB-данные) — тогда идти в Patent Public Search вручную, через браузер, не через автоматизацию.
- Старые сканы (доцифровая эпоха) по-прежнему без текстового слоя — это отдельное, не устранённое ограничение, актуально независимо от канала доступа.

## 4. Другие механизмы доступа (найдены поиском 08.09.2026, вне периметра готового скрипта)

Целевой поиск «есть ли официальный или готовый для LLM механизм, кроме прямого скрейпинга» дал три содержательных находки. Ни одна не встроена в `scripts/google_patents.py` — все требуют либо регистрации, либо стороннего Cloud-проекта, то есть решения и действия пользователя, а не агента. Зафиксированы здесь, чтобы не искать заново.

### 4.1. Google Patents Public Datasets на BigQuery — единственный официальный канал Google

У `patents.google.com` нет официального REST API — это подтверждено независимо несколькими источниками (не только эмпирикой раздела 2). Но у Google **есть** официальный путь к тем же данным: **Google Patents Public Datasets** на Google BigQuery — 166+ млн публикаций из 17+ юрисдикций, включая полный текст формулы и описания для US-патентов, доступ через SQL, без блокировок раздела 2 (это не сайт, а хранилище данных). Первый 1 ТБ обработки в месяц бесплатно, далее $5/ТБ. Требует Google Cloud аккаунт и проект — не подходит для мгновенного разового запроса, но для дела с большим объёмом поиска или регулярной практики это надёжнее и официальнее, чем `xhr/query`. Настройка — решение пользователя (создание GCP-проекта, включение биллинга), агенту не заводить это самостоятельно.

Источники: [Google Cloud — Google Patents Public Datasets](https://cloud.google.com/blog/topics/public-datasets/google-patents-public-datasets-connecting-public-paid-and-private-patent-data), [Google Cloud Marketplace листинг](https://console.cloud.google.com/marketplace/product/google_patents_public_datasets/google-patents-public-data).

### 4.2. EPO OPS (Open Patent Services) — официальный API за Espacenet

То, что публичный веб-поиск Espacenet отдал 403 (раздел «Порядок каналов» выше), не значит, что EPO не даёт API — даёт, отдельно от сайта. **EPO OPS** — официальный REST/XML сервис, свободная регистрация на `developers.epo.org` (~5 минут, без биллинга), OAuth2 (Consumer Key/Secret), бесплатный тариф до 4 ГБ трафика в месяц. Проверено 08.09.2026: `developers.epo.org` открывается (`200`), тестовый REST-запрос к `ops.epo.org` без токена корректно отвечает `403` (просит авторизацию, а не блокирует бота) — это работающий, ожидаемо защищённый сервис, а не мёртвый ресурс. По модели ближе всего к API Роспатента (ключ по регистрации, без верификации личности вроде ID.me у USPTO ODP) — регистрация опять же решение пользователя, агенту не проходить её самостоятельно.

Источники: [developers.epo.org](https://developers.epo.org/), [EPO OPS документация и обзор (patent-dev/epo-ops)](https://github.com/patent-dev/epo-ops).

### 4.3. Готовая библиотека для LLM-агентов: `patent-client-agents`

Нашёлся действующий, специально для ИИ-агентов написанный инструментарий: **`parkerhancock/patent-client-agents`** (Apache-2.0, 486 коммитов на момент проверки, активная разработка) — MCP-сервер + Python-библиотека, оборачивающая Google Patents, EPO OPS, USPTO ODP и ещё десяток юрисдикций единым интерфейсом. Предшественник (`patent_client`) того же автора архивирован 24.04.2026 именно в пользу этого проекта.

**Независимое подтверждение находок раздела 2** — их реализация `google_patents/client.py` использует ровно те же три ресурса, что найдены здесь вручную (`patents.google.com/patent/<ID>/en`, `patents.google.com/xhr/query`, `patentimages.storage.googleapis.com`), и их собственная документация прямо предупреждает: «Google may return an HTML "Sorry" page if it detects too many automated queries» — то есть блокировка из раздела 2 не случайность одной сессии, а известное, документированное поведение.

**Их подход к дисциплине запросов, вероятно, надёжнее, и `scripts/google_patents.py` уже подтянут под него** (было 1 с/1 повтор через 3 с — заменено на то же, что ниже):
- минимальный интервал между запросами — **4 секунды**;
- при `503` — не мгновенный переход к следующему источнику, а **cooldown 90 с**, затем повтор;
- до **4 попыток** с бэкоффом на каждый вызов;
- claims/описание извлекаются **парсингом HTML прямо со страницы патента** (`extract_claims()` по DOM), а не через PDF — они явно не сочли `/patent/<ID>` непригодным для использования, в отличие от вывода раздела 2.1 этой сессии. Вероятная причина расхождения — репутация конкретного IP тестовой сессии, а не свойство самого ресурса (см. правку раздела 2.1 выше). Наш скрипт по-прежнему идёт через PDF, а не DOM-парсинг страницы патента — проще и не зависит от структуры HTML.

**Не встроено в `scripts/google_patents.py`** — сторонняя, не проверенная нами лично библиотека, requires установку (`pip install patent-client-agents` или их MCP-сервер, есть и хостед-демо `mcp.patentclient.com`). Стоит рассмотреть как замену собственному скрипту, если понадобится больше юрисдикций сразу или более надёжная дисциплина запросов, чем то, что мы написали и проверили сами — но перед использованием проверить актуальность репозитория самостоятельно (в том числе автор архивировал предыдущую версию, эта тоже может смениться).

Источник: [github.com/parkerhancock/patent-client-agents](https://github.com/parkerhancock/patent-client-agents).

## Дисциплина исполнения

Общая с `search-rospatent.md`: 1 запрос/сек по всем источникам суммарно, дождаться ответа перед следующим вызовом; при отказе — пауза 3 с, одна повторная попытка, затем фиксация в три-счёте (запросов отправлено / документов получено / документов процитировано). Для Google Patents конкретно — см. раздел 2.3 выше, там дисциплина строже дефолтной.

## Что делать при отказе источника

- `patents.google.com/patent/<ID>` вообще не запрашивать (раздел 2.1) — использовать связку `xhr/query` + PDF.
- HTTP 503 / тело с «Sorry» на `xhr/query` → пауза в минутах (не секундах, не 3 с), затем переход к следующему источнику по списку выше; отказ фиксируется в журнале поиска (`search-workflow.md`), а не замалчивается.
- Скан без текстового слоя (в PDF или на USPTO) → пометить документ как «текст формулы не извлечён», не подставлять пересказ по памяти вместо дословной цитаты.
- Три подряд отказа по всем источникам → остановиться, сообщить пользователю, что именно недоступно, не продолжать поиск на догадках.

## CPC/МПК follow-up

После первичной выдачи по любому источнику извлечь CPC/МПК-классы top-5 хитов и выполнить один запрос, ограниченный этим классом — keyword-поиск систематически пропускает смежное искусство, которое class-restricted запрос находит. Для российского фонда индекс уточняется через `POST /classification/ipc/search/` (см. `search-rospatent.md`, раздел 6).

## Что не переносить из донора `research-patent/patent`

- Жёсткую привязку выпуска к DOCX через Node + `docx` — формат вывода выбирается задачей.
- Порядок «Google Patents первым» — для российского дела первым идёт API Роспатента.
- Англоязычные шаблоны разделов отчёта — писать по-русски, под форму ФИПС.
- Citation-graph через Lens.org (BYOK) — вне периметра этого скилла; для семейного разрешения по Google-хитам теперь достаточно `patent.family_metadata` из `xhr/query` (раздел 2.2) — отдельный скрипт не нужен; для российского фонда — `group_by` API Роспатента.
